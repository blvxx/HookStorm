# HookStorm

[English](README.md) | [Русский](README.ru.md)

**Проверяйте надёжность вебхуков до того, как ошибки попадут в production.**

HookStorm — локальная CLI-утилита для проверки обработчиков вебхуков в контролируемых условиях сбоев. Она отправляет реальные HTTP-запросы на выбранный вами endpoint, воспроизводит повторные и нестандартные доставки и проверяет ответы получателя, а при необходимости — состояние его бизнес-данных.

> **Статус: alpha (0.1.0a1).** Пакет пока не опубликован в PyPI. До первого релиза устанавливайте HookStorm из этого репозитория.

## Зачем нужен HookStorm

Интеграция вебхуков может успешно проходить обычный тест и всё равно ломаться, когда:

- провайдер повторяет запрос после таймаута, и платёж обрабатывается дважды;
- события приходят повторно или не по порядку и портят состояние приложения;
- получатель отклоняет правильную подпись или принимает неправильную;
- медленный ответ не укладывается в таймаут отправителя;
- обработчик фиксирует изменение в базе данных, но HTTP-подтверждение теряется.

HookStorm помогает воспроизводить такие ситуации с помощью повторяемых YAML-сценариев. Это **инструмент тестирования**, а не webhook relay, inbox, очередь или production-сервис доставки.

## Что умеет HookStorm

| Область | Возможности |
|---|---|
| Поведение доставки | Повторные попытки, экспоненциальная задержка, дубликаты, обратный порядок событий, ограниченная параллельность (до 50 событий), отложенный старт событий |
| Имитация сбоев | Ошибка соединения до отправки; имитация потери подтверждения после обработки запроса получателем |
| Подписи | Generic HMAC, Stripe, GitHub, Shopify и Standard Webhooks v1 |
| Проверки | Ожидаемый HTTP-статус, вложенные JSON-проверки по подмножеству, отдельные ожидания для дубликатов |
| Состояние приложения | Необязательный read-only GET-запрос после всех доставок; поддерживается Bearer- и API-key-аутентификация через переменные окружения |
| Диагностика | Проверка сценария, endpoint, секрета подписи, verification credentials, а также DNS/TCP/TLS-соединения по запросу |
| Отчёты | Автономный HTML, JSON и JUnit XML |
| История | Локальная SQLite-история запусков, очищенные JSON-baseline и сравнение регрессий по ошибкам, покрытию и задержкам |

При повторах и дубликатах сохраняются event ID и тело запроса. Подписи с временной меткой пересоздаются для каждой попытки. JSON- и JUnit-отчёты сохраняют исходный порядок сценария, даже если сетевые запросы выполнялись в обратном порядке или параллельно.

## Быстрый старт

**Требования:** Python 3.11 или новее.

После установки попробуйте автономную демонстрацию. Она поднимает временный receiver на
loopback, показывает повторную попытку и дублирующую доставку и сохраняет HTML-отчёт —
внешний endpoint не нужен:

```bash
hookstorm demo
```

### 1. Установка из исходников

```bash
git clone https://github.com/blvxx/HookStorm.git
cd HookStorm

python -m venv .venv
source .venv/bin/activate
python -m pip install .
```

**Windows PowerShell:**

```powershell
py -3.11 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install .
```

Для разработки и запуска тестов установите дополнительные инструменты:

```bash
python -m pip install -e ".[dev]"
ruff check .
pytest
```

### 2. Запустите демонстрационный receiver

Во втором терминале из каталога репозитория:

```bash
python examples/receiver.py
```

Receiver слушает только `127.0.0.1:8000` и предоставляет endpoints для проверки повторов, медленных ответов, подписей и потери подтверждения. Для его работы используется только стандартная библиотека Python.

### 3. Выполните первый сценарий

В терминале HookStorm:

```bash
hookstorm --version
hookstorm validate examples/payment-retry.yaml
hookstorm run examples/payment-retry.yaml \
  --target http://127.0.0.1:8000/webhook/flaky
```

Демонстрационный endpoint один раз возвращает HTTP 503, а затем принимает повторный запрос. По умолчанию HookStorm сохраняет HTML-отчёт в файл `hookstorm-report.html`.

## Сценарий — это обычный YAML

Пример отправляет событие создания заказа, повторяет запрос при выбранных HTTP-статусах и проверяет ответ:

```yaml
version: 1
name: Order webhook
retry:
  max_attempts: 3
  backoff_ms: 200
  retry_on: [408, 429, 500, 502, 503, 504]
events:
  - id: order.created
    event_id: evt_order_1001
    payload:
      order_id: order_1001
      total: 12500
    expect_status: [200]
    expect_json:
      accepted: true
```

Сначала проверьте конфигурацию без отправки запросов, затем запустите сценарий:

```bash
hookstorm validate scenarios/order.yaml
hookstorm run scenarios/order.yaml --target http://127.0.0.1:8000/webhook
```

Один сценарий может содержать от 1 до 500 событий. Размер payload каждого события ограничен 1 МиБ. Неизвестные поля и дублирующиеся YAML-ключи отклоняются, чтобы ошибки конфигурации обнаруживались заранее.

Полное описание параметров и ограничений находится в [руководстве по формату сценариев](docs/scenario-format.md).

## Основные возможности

### Повторы, дубликаты и порядок

- `retry.max_attempts` — общее количество попыток вместе с первой отправкой (1–10).
- `retry.retry_on` задаёт HTTP-статусы, при которых выполняется повтор. Таймауты и транспортные ошибки повторяются независимо от этого списка, пока остаются попытки.
- `delivery.duplicate_count` добавляет повторные доставки с теми же event ID и телом (0–100).
- `delivery.order: reverse` меняет порядок выполнения событий на обратный.
- `delivery.concurrency` запускает независимые события параллельно (1–50); повторы и дубликаты одного события остаются последовательными.
- `events[].schedule_after_ms` задаёт задержку старта события относительно начала всего запуска.

### Детерминированная имитация сбоев

Параметр `delivery.fault_injection` позволяет выбрать попытки для двух клиентских симуляций:

- `connect_error_attempts`: ошибка до того, как запрос попадёт к получателю;
- `response_loss_attempts`: получатель обрабатывает запрос, но HookStorm отбрасывает его ответ до получения подтверждения.

Это управляемые тестовые симуляции, а не сетевой прокси. Чтобы проверить реальное закрытие TCP-соединения получателем после фиксации изменения в БД, запустите `examples/commit-then-drop.yaml` с endpoint демонстрационного receiver `/webhook/commit-then-drop`.

Подробнее: [Неоднозначное подтверждение вебхука](docs/ambiguous-acknowledgements.md).

### Проверка подписей

Поддерживаются следующие провайдеры:

| Провайдер | Заголовок подписи |
|---|---|
| Generic | `X-HookStorm-Signature` |
| Stripe | `Stripe-Signature` |
| GitHub | `X-Hub-Signature-256` |
| Shopify | `X-Shopify-Hmac-Sha256` |
| Standard Webhooks v1 | `webhook-id`, `webhook-timestamp`, `webhook-signature` |

Для режимов `signature: valid` и `signature: invalid` задайте `HOOKSTORM_SECRET` в окружении терминала. Секреты Standard Webhooks должны иметь префикс `whsec_`. Не помещайте секреты в YAML и не коммитьте их в репозиторий.

Standard Webhooks реализован для v1 HMAC. Асимметричная подпись и ротация ключей пока не поддерживаются.

### Проверка бизнес-состояния после доставки

HTTP 200 сам по себе не доказывает, что заказ или платёж записан только один раз. Добавьте необязательный блок `verify`, чтобы после всех доставок выполнить read-only GET-запрос:

```yaml
verify:
  url: http://127.0.0.1:8000/__hookstorm/state
  expect_status: [200]
  expect_json:
    processed_events: 1
```

HookStorm передаёт заголовок `X-HookStorm-Run`, чтобы receiver мог вернуть состояние текущего запуска. Для проверки поддерживается Bearer- или API-key-аутентификация через переменные окружения. С точки зрения HookStorm probe является read-only; ваш endpoint должен предоставлять состояние без его изменения. Это проверка состояния, которое отдаёт ваш endpoint, а не универсальная гарантия exactly-once.

## Полезные команды

| Команда | Назначение |
|---|---|
| `hookstorm demo` | Запустить локальную демонстрацию retry и duplicate без внешнего endpoint |
| `hookstorm init --template stripe` | Создать стартовый сценарий с примером события и подписи провайдера |
| `hookstorm update-workflow` | Обновить SHA HookStorm в сгенерированном workflow после обновления |
| `hookstorm watch FILE.yaml` | Перезапускать сценарий при изменении YAML-файла |
| `hookstorm init` | Создать стартовый сценарий и GitHub Actions workflow |
| `hookstorm init --no-workflow` | Создать только сценарий |
| `hookstorm validate FILE.yaml` | Проверить YAML без отправки запросов |
| `hookstorm doctor FILE.yaml` | Проверить конфигурацию и обязательные переменные окружения |
| `hookstorm doctor FILE.yaml --connect` | Дополнительно проверить DNS/TCP и TLS; HTTP-запрос не отправляется |
| `hookstorm run FILE.yaml` | Выполнить сценарий с использованием `HOOKSTORM_TARGET_URL` (или указать `--target URL`) |
| `hookstorm export-pytest FILE.yaml` | Сгенерировать pytest-интеграционный тест |
| `hookstorm history list` | Показать последние локальные запуски |
| `hookstorm history show RUN_ID` | Посмотреть подробности запуска |
| `hookstorm history compare BASELINE_RUN_ID` | Сравнить последний запуск с baseline |
| `hookstorm history export latest --output baseline.json` | Экспортировать очищенный переносимый baseline |

Коды завершения: `0` — проверки пройдены, `1` — сценарий завершился, но одна или несколько проверок не прошли, `2` — ошибка конфигурации или выполнения.

Для локальной разработки задайте `HOOKSTORM_TARGET_URL` один раз и не передавайте
`--target` при каждом запуске `run` или `watch`. Явный `--target` имеет приоритет.
HookStorm не загружает `.env` автоматически: передавайте переменные через shell
или менеджер секретов.

`hookstorm watch scenarios/webhook.yaml` выполняет запуск сразу, а затем отслеживает
изменения файла с указанным интервалом (`--interval`, от 0.2 до 60 секунд). Ошибочные
изменения отображаются, но не завершают watch; после следующего изменения проверки
запустятся снова. Для остановки нажмите Ctrl+C. В интерактивном терминале также отображается прогресс каждой доставки; в CI и при перенаправлении вывода он не засоряет логи.

`hookstorm init --template` поддерживает `generic`, `stripe`, `github`, `shopify`
и `standard-webhooks`. Шаблоны содержат типичные примеры payload и формат подписи.
Это отправная точка, а не полная спецификация провайдера: адаптируйте данные и проверки
под свой receiver.

После осознанного обновления HookStorm выполните `hookstorm update-workflow` в репозитории
приложения. Команда меняет только SHA HookStorm в сгенерированном workflow и сохраняет
остальные настройки. Новый SHA берётся из установленной версии HookStorm.

## Отчёты и история

Формат отчёта выбирается через `--format html|json|junit`. По умолчанию создаётся HTML. JUnit формирует отдельный testcase для каждой доставки, включая дубликаты, и подходит для CI-систем.

По умолчанию история хранится локально в SQLite:

- Linux / macOS: `~/.hookstorm/history.sqlite3`
- Windows: `%USERPROFILE%\.hookstorm\history.sqlite3`

История и экспортированные baseline не содержат payload, HTTP-заголовки запросов, тела ответов и значения секретов. В них сохраняются служебные идентификаторы, например event ID, и target URL без query string. Проверяйте эти файлы перед передачей другим людям. В POSIX-системах каталог и файлы истории доступны только текущему пользователю.

JSON-baseline позволяет сравнивать запуски между отдельными CI jobs без общей SQLite-базы. См. [интеграцию с CI](docs/ci-integration.md).

## Безопасность по умолчанию

- **По умолчанию разрешён только loopback.** Команда `hookstorm run` блокирует удалённые цели, пока пользователь явно не разрешит их.
- Для удалённого HTTPS требуется `--allow-remote`.
- Для HTTP вне loopback нужны оба флага: `--allow-remote --allow-insecure-http`. Предпочитайте HTTPS.
- Перенаправления не выполняются, credentials внутри URL отклоняются, переменные окружения с настройками HTTPX proxy не используются.
- Тела HTTP-ответов читаются потоково с лимитом 2 МиБ. HookStorm запрашивает identity encoding и отклоняет неожиданное сжатие до декомпрессии.
- В отчёты не попадают payload, заголовки запросов, тела ответов и секреты. При этом отчёты содержат информацию о target и идентификаторы событий.
- Используйте изолированные development- или staging-данные. Не запускайте хаотические сценарии против production-платежей или критической инфраструктуры.

Подробнее: [Политика безопасности](SECURITY.md) и [Архитектура](docs/architecture.md).

## Интеграция с GitHub Actions

Выполните `hookstorm init` в корне репозитория вашего приложения. Команда создаст:

- `scenarios/webhook.yaml` — сценарий, который нужно адаптировать под ваш receiver;
- `.github/workflows/webhook-regression.yml` — готовый workflow для staging.

В GitHub Environment `staging` задайте `HOOKSTORM_TARGET_URL` как variable, а `HOOKSTORM_SECRET` как secret, если используются подписи. Созданный workflow пропускает pull request из fork-репозиториев, выполняет preflight до отправки событий и обновляет baseline только после успешного доверенного запуска из `main`.

Подробнее о настройке, baseline и защите staging: [Интеграция с CI в репозиториях приложений](docs/ci-integration.md).

## Ограничения и известные границы

- Не более 500 событий в сценарии; payload одного события — до 1 МиБ.
- До 50 параллельных независимых событий; до 100 дополнительных дубликатов на событие.
- Таймаут одного HTTP-запроса — до 5 минут. Общий бюджет запуска — 60 минут по умолчанию, настраивается до 24 часов.
- Лимит тела ответа — 2 МиБ; сжатые ответы отклоняются. JSON-значения сценариев, ответы, разбираемые для проверок, и импортируемая история ограничены 128 уровнями вложенности объектов/массивов.
- Клиентская симуляция потери ответа не является настоящим сетевым обрывом. Для теста реального TCP close используйте демонстрационный сценарий commit-then-drop.
- Standard Webhooks поддерживается только в режиме v1 HMAC.

## Разработка

```bash
python -m pip install -e ".[dev]"
ruff check .
pytest
python -m build --sdist --wheel --outdir dist
python scripts/smoke_wheel.py --all
```

CI проверяет Python 3.11–3.14 на Ubuntu, а также Python 3.12 на Windows и macOS. В каждой конфигурации запускаются lint и тесты, собираются wheel и source distribution, затем оба артефакта устанавливаются и проверяются в чистом окружении.
